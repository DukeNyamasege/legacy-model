Diagnosed syntax error root cause and architected comprehensive deployment fix

Two separate things happened. Only one of them is a real, recurring problem.

Root cause (the one that matters): broken syntax in app/repositories/rf_dir5_repository.py, currently on main (commit 3416f54). Inside settle_due_virtual_trades, a try: block starts at line 929, but before its except ValueError as exc: (line 945) there's a six-line fragment spliced in at lines 939–944 that doesn't belong there — an elif is_recovery: referencing target_stake/base_stake/reason, none of which exist in this function. Python can't have elif sitting between try: and its except, hence SyntaxError: expected 'except' or 'finally' block. That searched-for string ("Martingale disabled: one flat-stake PUT recovery is armed...") doesn't appear anywhere else in the codebase, so this isn't a duplicate of a real block — it's stray, orphaned code, safe to delete outright. I verified: removing exactly those 6 lines restores valid syntax, and I compiled every .py file in the repo afterward — nothing else is broken. This is why both api and worker are crash-looping: both import chains eventually hit app.rf_dir5_bot → app.repositories.rf_dir5_repository.

The failed to resolve host 'database' error is unrelated and almost certainly a one-off. It happened during the one-off migration container, right as deploy_vps.sh freshly created the legacy-model_test2 network in the same breath — Docker's embedded DNS occasionally isn't ready the instant a brand-new network comes up. I've added a single automatic retry for that step below; if it doesn't recur you'll never notice it.

Since your VPS flow does git reset --hard origin/main every deploy, hand-editing the file only on the VPS would get wiped on the next run — so the script below patches it automatically and verifies the whole tree compiles before it ever spends two minutes building an image again:

#!/bin/bash
set -e
cd /root/legacy-model

COMPOSE="docker compose -f docker-compose.yml -f docker-compose.vps.yml"

on_error() {
    echo
    echo "================== FAILED — DIAGNOSTICS =================="
    $COMPOSE ps || true
    echo "--- worker (last 150 lines) ---"
    $COMPOSE logs --tail=150 worker || true
    echo "--- api (last 150 lines) ---"
    $COMPOSE logs --tail=150 api || true
    exit 1
}
trap on_error ERR

One follow-up that isn't urgent but matters: this patch step will keep silently fixing the file on every deploy, which is fine short-term but means main on GitHub still has the bug baked in. Whoever/whatever you use to edit that repo (GitHub's web editor works fine for this) should delete those same 6 lines from app/repositories/rf_dir5_repository.py and push — once that's done, step 3b will just print "already fixed upstream, skipping" and you can drop it whenever you like.
